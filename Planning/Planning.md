# BoardGame Library API – Planning

## 0. Project context

### Goal
Build a small REST API for a personal board-game library. The API stores games locally in SQLite and lets users retrieve and filter the collection by supported player count.

### Problem / use case
A local board-game library should be easy to add to and query. The API focuses on a small, meaningful domain rather than external-data integration.

## 1. Direction

### Chosen direction
Personal Board Game Library REST API.

### Why
The domain is small enough for the assignment but meaningful enough to demonstrate REST, validation, persistence, filtering, HTTP semantics, async database I/O, and automated API verification.

### Explicitly excluded
- BoardGameGeek or other external API dependencies.
- Authentication/authorization for the library API.
- Background synchronization.
- Caching/Redis.
- Repository pattern without a concrete responsibility.
- Update/delete endpoints unless later required by the assignment.
- Pagination/sorting beyond the useful default title ordering.

## 2. Domain model

### BoardGame
- `Id` — local primary key generated by the database.
- `Title` — required, maximum 200 characters.
- `MinPlayers` — positive integer.
- `MaxPlayers` — positive integer and not below `MinPlayers`.
- `CreatedAt` — UTC timestamp set by the application.

## 3. API contract

### POST /api/games
Creates a board game.

Request:
```json
{
  "title": "Dune: Imperium",
  "minPlayers": 1,
  "maxPlayers": 4
}
```

Success: `201 Created` with the created resource and a `Location` header pointing to `GET /api/games/{id}`.

Validation failures: `400 Bad Request`.

Persistence failure: `500 Internal Server Error`.

### GET /api/games
Returns all locally stored board games.

Optional query:
- `players` — positive integer; returns games where `MinPlayers <= players <= MaxPlayers`.

Invalid `players`: `400 Bad Request`.

Database failure: `500 Internal Server Error`.

### GET /api/games/{id}
Returns one local game.

- Missing resource: `404 Not Found`.
- Non-positive ID: `400 Bad Request`.
- Database failure: `500 Internal Server Error`.

## 4. Behaviours

### B01 — Add a board game
A valid request creates and persists one valid local game and returns `201 Created` with a location for the new resource.

### B02 — Retrieve board games
GET returns the current local collection or requested resource without mutating state.

### B03 — Discover games by player count
`GET /api/games?players=n` returns games that support the requested player count.

### B04 — Reject invalid input
Invalid POST data and invalid IDs/query values are rejected with clear `400` responses and do not create invalid state.

### B05 — Handle persistence failures
Relevant database failures return a defined `500` response without exposing internal implementation details.

## 5. Design responsibilities

### Controller
Owns HTTP routing, validation at the API boundary, status codes, and response shaping.

### Service
Owns application behaviour and database queries. It performs async EF Core I/O and remains independent of HTTP concerns.

### Persistence
EF Core + SQLite. Production schema is managed through EF Core migrations. Tests use isolated in-memory SQLite.
